# Raccoon 每日领取状态误判：账单窗口太浅

日期：2026-10-19　范围：`vendor/channel-pack/src/raccoon-credits.ts` + 单测

## 背景（真机报障）

用户重启 DSH 后，Raccoon **两个账号都显示「今日未领」**，但当天早上 08:16 的自动签到
对两个号都完成了账单核实（各 +300，`auto-checkin.json` 记「raccoon: 2 个 +600积分」）。

Chief 用真实凭据查了上游账单，定位到根因：**今日那笔 +300 已经掉出插件的查询窗口**。

| 账号 | 今日 +300 在账单列表中的位置 |
|---|---|
| RaccoonMia (0899) | 第 **74** 位 |
| RaccoonAlexander (5173) | 第 **43** 位 |

而插件只拉 `paging.limit=20` 的第一页。

## 根因

账单是**按时间倒序的消耗流水**，而「每日积分发放」只是一条普通流水：

- 早上 08:00 `setting_info` 刚触发时，+300 是**列表第 1 条** ⇒ 在 20 条窗口内 ⇒
  当天早上的自动签到判定正确（这也是为什么「早上是好的」）；
- 用户用一个上午之后，几十条模型调用消耗把那条入账挤到第 43 / 74 位 ⇒
  **掉出第一页** ⇒ 状态查询判定「今天没有入账」⇒ 界面显示「今日未领」。

同时确认了两个**不能动**的既有实现（本次验证后保持原样）：

- 响应结构是 `data.items`（插件解析是对的）；
- `created_at` 形如 `2026-10-19T07:56:18+08:00`，上一任务的 `billDayKey`
  （解析成时间戳再换算 UTC+8）对这种形态判得对 —— **UTC 归一没问题，未改**。

另一个**必须避开的陷阱**：该接口的 `paging.total` **恒为 0**（上游说谎）。
任何「靠 total 判断是否还有下一页」的写法都会在第一页就停下，等于缺陷没修。

## 改动

`vendor/channel-pack/src/raccoon-credits.ts`（**一处修两处**：领取前的预检与
领取后的核实共用 `checkTodayGrantBills`）：

1. `RACCOON_DAILY_GRANT_BILL_LIMIT`：**20 → 100**。
2. 新增 `RACCOON_DAILY_GRANT_MAX_PAGES = 3`（100 × 3 = 300 条上限）。
3. `checkTodayGrantBills` 改为**分页拉取**，四条终止条件：
   1. 某页返回**不足 limit** ⇒ 到列表末尾；
   2. 某页**最旧一条的日键早于今天** ⇒ 列表倒序，再往后只会更旧，提前退出；
      ⚠️ 只在「该条时间**可解析**」时才用这条 —— 否则一条脏数据就能让整轮提前退出；
   3. 翻到 **MAX_PAGES**；
   4. （不 break）账号今天的入账找到之后仍继续翻到本轮结束 ——
      同一天可能有多笔入账（补发等），少翻一页会把合计算少。
4. **不使用 `paging.total`**（恒 0 的说谎字段），代码注释里写明了理由。
5. 第一页就失败 ⇒ 返回 `null`（无法确认，**不能**说成「未领」）；
   后续页失败 ⇒ 用已拿到的部分如实作答。
6. `TodayGrantCheck` 增加 `pages` 字段（诊断用）。
7. **翻满上限仍未找到**时，通过可选的 `warn` 回调记一行：
   `raccoon 账单已翻 N 页（300 条）仍未找到今日入账，按「未找到」处理`。
   ⚠️ 只是日志，**不改结论** —— 结论仍如实报「未找到」，因为可能是真没领，
   也可能是流水太深；只有日志能让人区分这两种。
8. `RaccoonAuth.fetchDailyGrantStatus` 把 `ctx.logger?.warn` 接进第 4 参。

## 测试（`scripts/raccoon-daily-grant-test.mjs`：11 → 21 项）

新增 10 项：

| 用例 | 断言 |
|---|---|
| 今日入账在第 **3 / 30 / 74 / 150** 位（跨页） | 都能检出，且翻页数 ≤ 上限 |
| `paging.total` 恒为 0 | 仍会翻过第一页（证明没被它骗停） |
| 某页不足 limit | 只请求一页就停（不空翻） |
| 最旧一条已早于今天 | 立即停止，且报「未领」（昨天的不算今天） |
| 今日入账在第 **400** 位（超出 300 上限） | 如实报未找到 + **留一行诊断日志**，且停在页数上限 |
| 第一页就失败 | 返回 `null`（不能误报「未领」） |
| 领取路径（第 74 位已入账） | `already-claimed`，**触发器一次都不调**（让触发器抛错来验证），且预检也翻页 |

## 语义变化（需要知道）

- **延迟**：状态查询从「1 次请求」变成「最多 3 次」。账单接口实测约 9 秒/次，
  故最坏从 ~9 秒变成 ~27 秒。已在 `MAX_PAGES` 的注释里写明这是刻意的取舍
  （面板刷新会慢，但不会再误报「未领」）。
  实际常见情形只需 1 页：今天的第一条流水早于 20:00 之前就会命中条件 2 提前退出。
- **未改判定口径**：仍然是「今天有 `points > 0` 的入账 = 已领」，只是**看全了**。
- **未改 UTC 归一**（`billDayKey`）：真机确认 `created_at` 是 `+08:00` 形态，现状正确。

## 边界

- 未改领取/触发器逻辑、未改版本号、未 `git push`。
- 300 条上限是**有意的诚实边界**：超出就报「未找到」并留日志，不臆造结论。
  若将来真有机器的日流水超过 300 条，日志会直接指出来（`仍未找到今日入账`），
  届时按日志把 `MAX_PAGES` 调大即可。
